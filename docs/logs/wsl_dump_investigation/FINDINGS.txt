WSL2 core dumps and --ulimit core=0: investigation notes (aalbino-1b, 2026-11-16)
Machine: Windows 10 laptop, WSL 3.0.5.0, kernel 6.18.58.1-microsoft-standard-WSL2, Docker Desktop (engine runs in the docker-desktop WSL distro, same VM kernel as Ubuntu-24.04).
Method: throwaway static program crash_test (crash_test.c, 64 MiB of touched memory, then SIGSEGV or abort()); runs in plain ubuntu:24.04 containers with varying limits; a dump of the whole image is ~67 MB (67,481,600 bytes), so a dump is easy to recognise. Raw outputs: experiments.txt, experiments2.txt.

ROOT CAUSE
/proc/sys/kernel/core_pattern = "|/wsl-capture-crash %t %E %p %s" (global to the WSL VM, read-only inside containers: "cannot create /proc/sys/kernel/core_pattern: Read-only file system").
For a PIPE core handler the Linux kernel does not apply RLIMIT_CORE as a size limit: a limit of 0 does NOT stop the handler from running and writing a dump. The only RLIMIT_CORE value that stops a pipe handler is exactly 1 (kernel treats 1 as the "recursive crash" guard and skips the dump). (Kernel behaviour, fs/coredump.c; confirmed empirically below.)

CONSEQUENCES FOR OUR JOBS
1. `--ulimit core=0` and `ulimit -c 0` never worked on this WSL kernel (pipe handler). Use exactly 1 byte: `docker run --ulimit core=1:1 ...` (verified E5/E6) or `prlimit --core=1:1 --pid $$` / `prlimit --core=1:1 <cmd>` inside the container (verified E12/E13; prlimit is in the ubuntu:24.04 image).
2. The run scripts I read begin with `ulimit -c 0` (mp14c_noloader_run.sh, mp14d/e/f_win_run.sh, mp14e..mp14i dzn/win scripts; I did not check every file, e.g. run_mp14d_real.sh). Under `--ulimit core=1:1` that line LOWERS the limit to 0:0 and RE-ENABLES the dump (E14). Remove it (or replace by `prlimit --core=1:1 --pid $$`). bash cannot express 1 byte (`ulimit -c 1` = 1024 bytes, E0b).
3. Anything that sets RLIMIT_CORE to 0 inside the process re-enables dumps (E7/E14): the unit-test harness of the server does this (do not run it on WSL), mongod itself does not (per mongo-26's source grep).
4. Verification to build into runners: after starting mongod, `grep 'core file' /proc/$MP/limits` must show "1 1 bytes"; and `ls /mnt/d/wsl/crashes` before/after.
5. A prctl(PR_SET_DUMPABLE,0) supervisor is useless across execve (E11); setting it inside the target program works (E9) but needs source changes.

WSL-LEVEL SETTINGS (not applied; user approval needed)
.wslconfig [wsl2] crashDumpFolder (default %TEMP%\wsl-crashes) and maxCrashDumpCount (default 10) exist and are active here (D:\\wsl\\crashes, 2). `wsl --help` has no crash/dump option. Setting maxCrashDumpCount=0 is reported to be handled by newer WSL (a PR fixed a service crash at 0) but I did not test it (needs a .wslconfig edit and wsl --shutdown). A global fix would be `sysctl kernel.core_pattern=core` inside the WSL VM (needs root, lost at VM restart); not done.
