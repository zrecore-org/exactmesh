# 3D mesh workstream: library evaluation and GPU acceleration with CPU fallback

Approved plan (2026-11-14), kept as the pre-registration record of this project: bars and kill criteria were written **before** the runs they govern, and amendments are
recorded with their reasons. It was written during the research phase on a research branch of a fork (see `PROVENANCE.md`); paths of the form `mesh/...` there are the root of this
repository here, `poc12_f64soft.cpp`-style references name research-history files that are not part of this repository, and "the project owner" is the person who owns this project. Standalone proofs of concept only:
no third-party source is committed (libraries and meshes are fetched, pinned and checksummed), and negative results are recorded plainly.

## Questions
1. Which permissively licensed libraries can provide SFCGAL-class operations (3D first, then 2D), and how much of SFCGAL's function list
   is covered, partly covered, or needs our own code?
2. Can a GPU speed up predicates, distance, point-in-solid, volume and candidate culling while giving exactly the CPU's answer?

## Exactness contract (tiers)
1. GPU on == CPU only, same build. Hard.
2. Same binary and input, same bytes at any thread count (library booleans: serial build, `-ffp-contract=off`, pinned version). Hard; gates G1.
3. Library boolean output identical across x86_64 and arm64. Measured and reported, not required; if it fails, booleans are "same shape within a stated tolerance".
4. Our own predicates and measures (intersects, point-in-solid, distance, volume by exact accumulation) identical everywhere. Hard.

Vocabulary: **wrong** = silently incorrect result (must be 0); **refused** = clean error (counted, acceptable); crash or hang = failure.

## Wave 0 (started)

### MP01 corpus + harness (`corpus/`, `harness/`)
Question: can one reproducible mesh corpus feed every library, GPU kernel and oracle?
Steps: a compact binary mesh format (float64 xyz, uint32 triangles) with reader/writer; generators for sphere, torus, icosphere, grid; adversarial
pair generators with an expected outcome per case (coplanar, touching at vertex/edge/face, shared edge/vertex, slivers, nested, identical, A minus A,
open/non-manifold, self-intersecting, 1 ulp / 2^-20 / 2^-40 perturbations, huge offsets); many-small and few-large sets; a pinned fetch script for
Thingi10K (fetched only, never committed; per-model licenses vary, see `CORPUS.md`).
Pass bar: the corpus is byte-reproducible from the scripts and every case carries a tag.

### MP02 oracles and comparison (`oracle/`, `harness/`)
Question: what do we compare library and GPU answers against, without GPL code?
Steps: Shewchuk `predicates.c` (public domain, fetched, pinned) for orient2d/orient3d/incircle/insphere; exact rational recompute with
Boost.Multiprecision `cpp_rational` (Boost headers fetched by `third_party/fetch.sh`) for orientation, volume, area on small cases; canonical equivalence for
booleans (exact volume, area, Euler characteristic, components, watertightness, sampled point-in-solid), never bit-for-bit across libraries;
planted mutants (a check that cannot fail proves nothing); a Geogram cross-check once MP04 exists. CGAL is not used.
Pass bar: every planted mutant is caught; Shewchuk and the rational recompute agree on 1e7 random plus adversarial predicate inputs.

### MP06 parity matrix and license audit (`PARITY.md`, `parity.csv`, `LICENSES.md`)
Question: how much of SFCGAL v2.3.0 do the permissive options cover?
Steps: every SFCGAL function (types, predicates and measures, constructive, skeleton/alpha/visibility, transforms) mapped to Manifold, Geogram, Embree,
Clipper2, Boost.Geometry, earcut, CDT, S2 (spherical only), write-ourselves (with a size estimate) or infeasible; columns for "needs exactness" and "GPU-able";
every license re-verified at a pinned tag from the project's own LICENSE file (agent claims are not evidence). Done 2026-11-14; findings: Geogram bundles restricted components (see MP04), CDT is MPL-2.0 (weak copyleft, not counted as permissive), the in-tree S2 is spherical only, Boost.Geometry is not vendored.
Pass bar: every SFCGAL function has a row; coverage percentages for 3D and 2D separately, with and without write-ourselves items.

Wave 0 is done when: the corpus is byte-reproducible, every mutant is caught, the predicate oracles agree, and every SFCGAL function has a parity row.

**G1 boolean engine:** Manifold passes with 0 wrong on valid manifold input, clean refusal of non-manifold input, and tier-2 determinism (tier 3 reported only). Geogram is promoted only if Manifold fails tier 2 or shows wrong results.
**G2 GPU filter:** 0 wrong definite signs on at least 1e9 random plus all adversarial inputs; uncertain rate reported (suggested bars: under 1% random, under 10% on Thingi). If not met: fix the bound, switch to the integer path, or drop the GPU predicate stage.

## Pre-registered pass bars for the library evaluations (MP03, MP04)
Fixed on 2026-11-14, **before any library output was scored**. Scoring tool: `mesh_compare score` (`oracle/compare.cpp`, with `harness/pip.h` and `harness/topology.h`), self-tested by `mesh_compare selftest`
(accepts known-good results, fails seven kinds of wrong result, catches two planted bugs in the exact point-in-solid test). Every library is run on the 31 corpus cases x 3 operations (union, intersection, difference), 60 s timeout each. A change to any bar after the first scored run is recorded as a change, with the reason, and everything is re-scored.

- **Verdict per case and operation:** PASS, FAIL, REFUSED (library exit code 3: it declined the input), ACCEPTED-UNVERIFIED (the inputs are not valid solids and the library returned a closed result), TIMEOUT, CRASH.
- **Valid inputs (tag `valid`):** 0 FAIL, 0 TIMEOUT, 0 CRASH. A PASS needs all of: the result is empty or a closed, edge-manifold, non-inverted mesh with no duplicated triangle; for box pairs the exact volume equals the manifest's exact expectation or differs by at most 1e-9 relative to it (expected zero: at most 2^-52 of the larger input volume), classified exact / close / wrong, and "wrong" fails; every cell of the box-pair arrangement (per-axis midpoints of the sorted box coordinates plus an outside cell) and 5,000 exact dyadic sample points for every pair classify the same way in the result as in the boolean of A and B (points on a surface are skipped and counted). Refusals of valid inputs are counted and listed with the library's reason; more than 3 of the 24 valid cases x 3 operations refused is reported as a robustness concern for the project owner to weigh, not an automatic fail. Zero-area triangles in a result are reported, not failures.
- **Malformed inputs (tags `open`, `non-manifold-edge`, `self-intersecting`, `unwelded-vertices`, `zero-area-triangle`, `inverted`, `duplicate-triangle`):** acceptable outcomes are REFUSED or ACCEPTED-UNVERIFIED with a closed manifold result; a non-closed result, a crash or a timeout is a FAIL.
- **Curved pairs** have no exact expected volume, so the point tests arbitrate; where both libraries succeed their exact volumes are also compared (relative 1e-9, informational).
- **Tier 2 (determinism):** two runs of the same serial binary give byte-identical output (sha256) on every case: hard, any difference fails tier 2. Builds with and without `-ffp-contract=off` give identical bytes: reported; any difference means the product build must pin the flag.
- **G1 rule:** Manifold passes G1 if it meets the valid-input and malformed-input bars and tier 2. Geogram (permissive build, after the `nm` check shows no TetGen, Triangle or HLBFGS symbols) becomes the primary only if Manifold fails G1; if both pass, the choice uses the speed table, refusal counts and the project owner's view of Geogram's reduced feature set.
- **What the tool cannot see (stated now, not discovered later):** the volume check is exact only for box pairs; curved pairs are sampled, so a feature thinner than about 1/5000 of the sampled volume can be missed; arrangement cells whose midpoint is not a representable double (the one-ulp gap case) are checked by the exact volume only; a vertex moved by 2^-45 stays inside the 1e-9 volume tolerance; the point tests use closed, outward or inward oriented meshes and are meaningless for the malformed inputs, which is why those are judged by structure only.

### Changes to the pre-registered bars (each recorded with its reason; results re-scored)
1. **2026-11-14, after the first Manifold scoring run: manifoldness of a result is judged as returned (by vertex index), not after welding coincident vertices.** Reason: my first implementation welded vertices with equal coordinates before checking edges, so the correct union of two boxes
   that touch along an edge (geometrically a non-manifold solid) was reported as "not a closed manifold" although Manifold returned a valid manifold (16 vertices, every edge shared by exactly two faces, the touching edge's endpoints duplicated). That was a defect in my bar, not in the library.
   Effect on Manifold: 4 verdicts changed (`box_edge_touch` union FAIL to PASS; the three `bad_nonmanifold_edge` results FAIL to ACCEPTED-UNVERIFIED); the other 89 verdicts are unchanged. The first-run results are kept in `lib/manifold/scoring_results_first_scoring.tsv`. The geometric (welded) property is still reported as `geomClosed`.
   Also fixed before the first run was scored: the code only applied the "non-closed result is a FAIL" rule to valid inputs, while the registered text applies it to every input; the code was changed to match the text.
2. **2026-11-14, clarification of the Geogram license check (MP04):** the registered wording ("no tetgen, triangle or HLBFGS symbols") cannot be met literally, because Geogram's own BSD files carry those names (`delaunay_tetgen.cpp`, `delaunay_triangle.cpp`, `triangle_intersection.cpp`; the first compiles to one marker symbol `_dummy_delaunay_tetgen_compiled`).
   The check that matters is: (a) no compiled file under `third_party/{tetgen,triangle,HLBFGS}`, from `compile_commands.json`; (b) zero symbols from the restricted libraries' own APIs (`tetgenio`, `tetgenbehavior`, `triangulateio`, `INIT_HLBFGS`, `HLBFGS_*`) in every artifact. Both pass (checked by me, not only by the sub-agent).
3. **2026-11-14, after the Geogram scoring run (advisor's review): structure check made symmetric.** Amendment 1 judged manifoldness by vertex index only, which accepted Manifold's representation of an edge-touching union (endpoints duplicated) but rejected Geogram's (edge shared by four faces), although the exact union of two solids that touch along an edge or at a corner is geometrically non-manifold and both representations are valid.
   A result now passes the structure check if it is a closed manifold as returned OR it has no boundary edge after identifying coincident vertices (so it may have an edge or vertex shared by more than two faces); open surfaces still fail; the volume and point tests still apply.
   Effect: Manifold unchanged (57 PASS, 15 FAIL valid; 12 refused, 6 accepted, 3 pass malformed); Geogram valid 63 PASS, 9 FAIL for both thread settings (its `box_edge_touch` union now passes), malformed 14 accepted, 6 pass, 1 FAIL. Both libraries were re-scored.

## MP17 (added 2026-11-14): exact plane-based integer boolean, cost and fidelity POC
**Question.** Can a fixed-width integer (plane-based) boolean give exact answers below Manifold's 1e-12 floor at a cost that beats the published exact engines, with no GPL or unlicensed code?
**Basis (verified by me from the survey's formulas, `lib/planebased/SURVEY.md`):** plane coefficients need b >= 9L + 18.6 bits for L-bit grid inputs (my recomputation: L=26 -> 253, L=40 -> 379, L=43 -> 406, L=53 -> 496). 256-bit (the published width) covers L <= 26 only. Code: none usable (EMBER binary only; octree-BSP and Campen-Kobbelt unreleased; the third-party port depends on an unlicensed library and is not exact). So this is a clean-room implementation from the papers' maths; I do not read or copy the unlicensed repo.
**Stated limit before any result:** snapping inputs to an L-bit grid is itself a rounding of relative size 2^-L. L=40 equals Manifold's 1e-12 class, so it does not beat it. Only L=53 (512-bit) matches binary64 mantissa resolution relative to the bounding box, and even then arbitrary binary64 (exponent range 2^2098) is not representable without bignums.
**Steps and bars (registered before running):**
1. Cost of the core predicates at widths 256/384/512 bits (plane through 3 integer points, plane-plane-plane vertex sign, point-plane side) on a fixed-width integer class written for this POC, vs Shewchuk orient3d and vs `cpp_int`. Report ns/op on M1 and the 32-bit-limb op counts (GPU suitability). Bar: report only.
2. Exactness: every result equals the Boost.Multiprecision `cpp_int` recompute on 1e7 random plus adversarial inputs at L = 26/40/53 (0 differences, hard), with planted mutants (carry drop, wrong sign) all caught. Add an **extreme class** at coordinates of +/-(2^L - 1) and other maximal-determinant inputs: random inputs almost never reach the magnitude limit, so this class is what shows the width is enough. The 9L + 18.6 bound comes from the octree-BSP paper (Sec 3.2), whose constants include octree cell planes; **I derive the bound for this POC's own predicates** and check it against the extreme class.
   **No new planes:** exactness without width growth requires that no plane is ever built from a constructed (intersection) vertex; planes come only from input triangles. Output vertices are exact rationals rounded to nearest binary64 on output, and `mesh_compare` scores the rounded mesh (so the rounding can itself fail a case; reported).
3. **Width census first (before the integer class is written):** run every previously failing valid case through `toCommonInts` (`harness/exact.h`) after the same exact re-centring as before and record the integer width L each needs. Then the rule, fixed now: cases with L at or below the chosen width are scored against the **original, unsnapped** input with `mesh_compare` and must show 0 FAIL; cases above it are reported as OUT-OF-RANGE or refused. **Nothing is snapped and then scored.** Cases counted by distinct name: the union of Manifold's 15 and Geogram's 9 valid-input failures (they share the 6 offset cases), so the census lists each name once with which library failed it.
4. Speed vs Manifold and Geogram on the same cases (honest: single thread, include the quantization step).
**Kill criteria (numbers fixed now):** if the unfiltered 512-bit integer plane-plane-plane sign costs more than 50x the time of Shewchuk's adaptive `orient3d` on the same random inputs (M1, single thread, one-time measurement), or step 3 needs more than the plane-based core plus a simple arrangement to pass, stop and record why.
**Census result (2026-11-14, `RESULTS.md`):** the 7 distinct failing names need L <= 53, so the registered width is **512-bit**; curved cases (L = 57-59) are OUT-OF-RANGE at 512.
**Outcome (2026-11-14):** steps 1-2 exactness bars met; kill criterion triggered at 800x (RESULTS.md); steps 3-4 not run. MP17 stopped as registered.
**Out of scope:** GPU kernels (step 1 only counts limb ops), octree acceleration, non-manifold repair, production API.

## MP18 (added 2026-11-14): scope and repair Geogram's corner-contact failure
**Question.** Geogram (exact predicates, BSD, v1.10.1 and `main` e6f8667a) returned a one-box result for `box_vertex_touch` (union volume 1 instead of 2). How wide is that failure, and can a cheap exact guard around the call remove it without changing results elsewhere? A guard that works would make Geogram, not an integer engine, the route to sub-1e-12 fidelity.
**Step 1, scope it (registered before any run).** Add an exact-integer corpus family `touch_*` (new generator code, expected volumes exact): at least 24 pairs covering vertex-vertex, vertex-on-face, vertex-on-edge, edge-edge touching at a point, edge-on-face, and oblique versions (integer shear and axis-permuted copies), built from boxes, tetrahedra and octahedra, each for union, intersection, difference. Scored by the existing `mesh_compare` rules. Report Geogram's verdict per case and which touch classes fail. Not run on Manifold's results table.
**Step 2, root cause (time-boxed to reading `mesh_surface_intersection*` and the boolean flags, plus one probe per hypothesis).** Say what the library does, from its source; mark anything not read as unverified.
**Step 3, guard.** Candidate guards, each written with exact predicates only (`harness/exact.h`): (a) exact bounding-box contact test (zero-extent overlap on some axis => result is the trivial composition); (b) a post-check that an exact point-in-solid (`harness/pip.h`) classification of sampled result-vertex neighbourhoods agrees; (c) any guard the root cause suggests. Bars: **0 FAIL on the `touch_*` family; 0 verdict changes on the existing 93 rows; no more than 10% added time on non-touching pairs** (median over the corpus); the guard must never alter a result Geogram got right (compared byte for byte on the 63 passing valid cases). Planted mutants of the guard (skipped axis, off-by-one in the contact test) must be caught by the family.
**Kill criterion:** if the failure turns out to reach generic overlaps (not only contact), or no exact guard meets the bars, record that Geogram cannot be made safe by wrapping and stop.
**Out of scope:** patching Geogram's source, GPU work, non-manifold repair.

## MP10 (registered 2026-11-14, Wave 2): deterministic GPU LBVH and box-pair emission
**Question.** Can the GPU find all overlapping triangle-box pairs between two meshes (or many small meshes batched in one dispatch) with a result that is **identical to the CPU answer** and independent of tree shape, thread scheduling and device, using only 32-bit atomics?
**Design (fixed before running):** boxes are binary64 triangle boxes rounded **outward** to binary32 on the host (so the GPU pair set is a superset of the exact binary64 box overlaps); 30-bit Morton codes of box centres; the existing stable radix sort kernels (`shaders/sort_*.comp`); Karras parallel radix tree with equal codes separated by position; bottom-up box fitting with a 32-bit `atomicAdd` per internal node; query kernel with an explicit stack, count pass then emit pass at prefix-summed offsets; a final canonical sort of each query's hits by B index (the tree shape never reaches the output). A pair cap with CPU fallback on overflow.
**Bars (all hard unless marked reported):** (1) the sorted pair set equals the pair set of an exact CPU reference on the **same binary32 boxes** (brute force up to 4e8 box tests, `cpu/bvh_ref.h` beyond that on the widened boxes): 0 differences on every class: uniform random, clustered, all-identical boxes (equal Morton codes), face/edge/corner-touching lattice, zero-extent boxes, a few huge boxes among small ones, many small meshes batched (1000 meshes x 100 boxes, offset in space), and few large (1e6 x 1e6). (2) **Superset:** for real meshes (the corpus primitives, translated) the GPU pairs contain every pair found by `bvh_ref` on the binary64 boxes (0 missing); the false-positive rate from rounding is reported. (3) **Determinism:** 20 repeats give byte-identical pair lists; M1, lavapipe x86_64 and aarch64 (and the T4 at the gate) give identical lists. ## V1 (registered 2026-11-14): validator nesting and orientation
**Gap.** The MP26 real-mesh run found that the exact input validator (`lib/geogram/mp21b/validator.h`) checks only the sign of the TOTAL exact volume. It accepts a same-orientation shell nested in another, a negative-volume component beside a larger positive one, and (by design indistinguishable) an inverted inner shell.
**Semantics (fixed now, before any code).** A mesh is a union of components (edge-connected sets of triangles after welding by exactly equal coordinates; after the existing edge checks every edge has one triangle per direction). For each component the validator computes the EXACT signed volume (Boost cpp_int, `exactVolumeTimes6` convention; a double filter may only shortcut a certain sign). Component B *contains* component A when one vertex of A that is not on B's surface lies inside B by the exact ray-parity point-in-solid test of `harness/pip.h` (symbolic tie-break, exact orient2d/orient3d; reimplemented on cpp_int inside the validator so it needs no extra library). The depth of a component is the number of components containing it; its parent is the container of greatest depth. A component is accepted iff (1) its exact volume is non-zero, and (2) its sign is OPPOSITE to its parent's (a solid inside a cavity inside a solid is allowed: signs alternate +, -, +, ...), and a component with no parent is positive. Violations are refused with a reason code at the head of the reason string:
* `V1-ZERO-VOLUME-COMPONENT` a component has exactly zero signed volume;
* `V1-NEGATIVE-OUTSIDE` a negative-volume component with no container (not inside any positive component);
* `V1-NESTED-SAME-ORIENTATION` a component whose sign equals its parent's (a solid inside a solid with no separating cavity, or a cavity inside a cavity);
* `V1-CAVITY-NOT-ALLOWED` only when the caller sets `allowCavities=false` (strict mode): any negative component. Default is `allowCavities=true`, because an inverted inner shell strictly inside a positive one is a legitimate hollow solid and the validator cannot know the caller's intent; the number of cavities is returned in a report so a caller can see it;
* `V1-SURFACES-SHARED` every vertex of A lies on B's surface (the nesting question cannot be decided from vertices); `V1-NESTING-INCONSISTENT` two non-nested containers of one component (can only happen when component surfaces cross).
Existing behaviour kept: the total-volume check and its reason ("inverted orientation") run first, so a single inverted mesh keeps its old reason; two closed pieces touching at a vertex stay valid; **crossing or touching component surfaces are NOT detected in general (the validator has no self-intersection check, `docs/LIMITS.md`); the nesting decision is exact only for components whose surfaces do not cross.** Single-component meshes (the common case) pay only for the component labelling.
**Resolution of one conflict in the request.** The known-limit case (a) (an inverted box strictly inside a box) is by the legitimate-cavity rule ACCEPTED in the default mode and refused only in strict mode (`V1-CAVITY-NOT-ALLOWED`). Cases (b) same-orientation nested shell and (c) negative component beside a positive one are refused in the default mode.
**Bars.** (1) the three known-limit inputs: (b) `V1-NESTED-SAME-ORIENTATION` and (c) `V1-NEGATIVE-OUTSIDE` refused in default mode, (a) accepted as a recorded cavity in default mode and refused `V1-CAVITY-NOT-ALLOWED` in strict mode. (2) 0 false refusals on (i) every currently accepted valid corpus (the G1, fidelity and fidelity2 generators' valid counts and their recorded file hashes unchanged; the 9,453-row pipeline verdict-list hash `e2edd6f7...` unchanged if the pipeline can be rebuilt locally) and (ii) a new generated set of legitimate cavity cases (`corpus/v1`, class `legit`: box with box cavity, sphere with sphere cavity, nested two-level cavity-with-island, several cavities, extreme coordinates, one-ulp-gap cavities, side-by-side solids). (3) 0 wrong accepts on a fresh generated set of at least 200 invalid nesting/orientation cases (`corpus/v1`, class `invalid`; generator source hash and the set's EXPECTED_SHA256 recorded before the validator is changed or run on it), each refused with its expected reason code. (4) planted mutants each caught: `MUT_V1_NOSIGN` (skip the sign rule), `MUT_V1_NONEST` (skip the nesting test), `MUT_V1_DOUBLEVOL` (component volume in plain double); caught means the corpus checker exits non-zero AND the unit suite fails. ## V3 (registered 2026-11-14): why do one-ulp cavity cases fail (diagnosis, no pipeline change)
**Question.** In the V2 cavity run (256 pairs, 768 rows) 8 rows FAIL and 6 are refused with the Geogram exception `!point_outside_boundary`, all in the `one_ulp_cavity` family (cases 050 to 053). `docs/RESULTS.md` (V2) attributes them to "the Boolean engine on valid cavity inputs" and, in passing, to "vertex rounding in a gap of one ulp". Which of the mechanisms below is it?
**Facts known BEFORE any new run (read from the V2 result files, `build/work/v2_cavity/run/out_*/results.tsv`, and the generator `corpus/v1/gen_v1.cpp`).**
(1) All 8 FAIL rows log `path=c0 s=0 c=(0,0,0) translate_back_max_err_ulps=0 rounded_coords=0/N`: for them the pipeline's scale-back and translate-back are the identity, so the pipeline's own output rounding cannot be the cause (hypothesis H1 as worded in the request is already refuted for these rows by the logs; it is still checked, not assumed). The rounding that remains is Geogram's own: `find_or_create_exact_vertex` turns every constructed exact point (homogeneous expansions) into a double with `PCK::approximate`, whose source says "TODO: find a way of computing the round to nearest approximation" and which computes `estimate(x) / estimate(w)` (two or three roundings, not a correctly rounded quotient).
(2) The generator has no random numbers: cases 050 and 052 are the same pair of meshes, as are 051 and 053 (checked with `cmp` on A and B for cutA and cutB: identical; output hashes match in the results). So there are 4 distinct failing results (2 distinct FAIL results of 050/052 cutA union and difference, 2 of 051/053 cutB intersection and difference) and one distinct exception input (050/052 cutB, identical for all three operations). Duplicates are not independent evidence.
(3) Cases 050/052 use the cavity box `{l,1,1}..{2,2,2}` with `l` the smallest subnormal; the wall is x in [0, l]. B (cutA: x in [1.48, 5.2]; cutB: x in [0.452, 2.828]) never touches that wall. So for 050/052 the trigger cannot be B meeting a one-ulp wall; the candidate is the subnormal coordinate itself (expansion arithmetic underflows) or the cavity. Cases 051/053 use `{1,1,1}..{u,u,u}`, u = nextafter(4, 0), walls [u,4] of one ulp; cutB crosses the y wall region, cutA also crosses walls and passes.
(4) Geogram's `point_outside_boundary` assert is in `CDTBase2d::locate` (`delaunay/CDT_2d.cpp`), used both by the remeshing of intersected triangles and by `simplify_coplanar_facets`; which stage throws is not known.
**Hypotheses (mutually exclusive as the primary cause of a row).**
* H1' (rounding of constructed vertices): Geogram's exact output (the rational `exact_point` of each vertex) is correct; the failure appears only when those points are converted to doubles (non-correctly-rounded `approximate`), moving or collapsing thin features. The pipeline back-transform is excluded by fact (1) and is reported as a sub-case only if it is ever non-identity.
* H2 (engine misclassification): the exact (rational) output of Geogram is already wrong (wrong cell kept, wrong topology, wrong exact volume), specific to cavities.
* H3 (subnormal or one-ulp features in general): the exact output may or may not be right, but the same failure signature appears with no cavity (a positive box with a subnormal coordinate, a one-ulp plate, two boxes one ulp apart, two boxes overlapping by one ulp). H3 is about the cause being the feature, not the cavity; it is combined with H1' or H2 for the mechanism.
**Method.** All code is new and in `lib/geogram/v3/`; the frozen sources are not edited.
(a) Instrumented copy of the CLI (`geogram_fidelity2_v3.cpp`, a copy of `lib/geogram/mp24b/geogram_fidelity2.cpp` with `mesh_boolean_operation` inlined, built with the same flags and the same patched library, `build_v3.sh`). It runs the same pipeline stages (validate, scale, re-centre, Geogram intersect / classify / simplify, translate-back, scale-back), and additionally dumps, in the scaled and re-centred frame, the exact homogeneous expansion components of every constructed output vertex before `approximate`. **Gate:** in default mode the copy must reproduce the output hashes of the V2 CLI on the 8 FAIL rows (`96e0f1cb...`, `b26488fa...`, `533e6f75...`, `e41a1444...`) and its dump must contain the same triangles; otherwise no dump is used. `v3_analyze.py` then computes, with exact rationals (Python `Fraction`, and the existing `mesh_compare` for the V2 verdict): the exact volume of the rational-vertex mesh and of the rounded mesh, each against the exact expectation in that frame (the manifest values, frame s=0, c=0 for these rows); zero-area, flipped (negative-orientation) and off-plane triangles (every face of every exact result here is axis-aligned, so a triangle whose three vertices do not share one coordinate value on an axis is the signature of vertex rounding); the vertices that differ from the rational point by more than 0 ulp; and, replicating the scorer's `mt19937_64(12345)` sample loop, the sample point(s) classified differently and their classification against the exact-vertex mesh and the rounded mesh. Probe (ii): the same run with `MESH_BOOL_OPS_NO_SIMPLIFY`.
(b) Non-cavity control (`make_control_pairs.py`, same corpus layout and scorer as the cavity pairs, run with `run_control_pairs.sh` through the unchanged V2 CLI): at the failing frame (origin, L = 4, B boxes from the same fractions of [0,4]^3 as in the cavity pairs) and, for the plates, also scaled by 2^30 so that the pipeline's scale path (s > 0) is exercised: S1 a positive box with a subnormal coordinate (`{l,1,1}..{2,2,2}`) or a coordinate one ulp below 4 (`{1,1,1}..{u,u,u}`), no cavity; S2 one-ulp-thick or subnormal-thick plates at either end of an axis; S3 two boxes one ulp apart (gap l at the origin, gap 2^-51 at 2); S4 two operands overlapping by one ulp. Variants of B: contain, disjoint, cutA, cutB (S1 to S3), a fixed overlap pair (S4). Exact volume expectations for all (every operand is a union of axis-aligned boxes). Far offsets are not added (they only add hard-limit refusals and would pad the count); rows REFUSED are reported separately and are not counted as a pass. At least 60 pairs, 3 operations each.
(c) The exception input (050/052 cutB, one distinct pair): the failing stage (intersect, classify, simplify) is caught separately in the instrumented copy; then one probe per hypothesis on the operand A, all with B unchanged: P1 (subnormal) replace `l` by normal values 2^-1022, 2^-540, 2^-300, 2^-100, 2^-52, 2^-30 (a ladder: where does the exception stop?); P2 (cavity) the control S1 box `{l,1,1}..{2,2,2}` without the outer box, same B; P3 (thin wall) the cavity with `l` = 2^-52 and 2^-30 (wall thin but normal). Results labelled verified (reproduced) or unverified (not run, or not reproduced).
**Decision rule (registered before the run).**
* If the rational (pre-rounding) output is exactly right on the FAIL rows (volume equal to the expectation, no flipped or collapsed triangle, sample points classified correctly) -> H1' for those rows, and the engine's classification is not at fault; if in addition the non-cavity control shows the same signature (FAIL rows of the same type: volume off by output rounding, one sample point flipped, or the same exception with a subnormal coordinate) -> "one-ulp or subnormal features in general, not cavities".
* If the rational output is already wrong and the control passes (0 FAIL in the non-refused control rows) -> a cavity-specific engine problem; then propose an exact test that refuses a nested component only when its separation from its container is below a stated bound, and state whether it can be made exact.
* If the rational output is wrong and the control also fails -> H3 with an engine fault (not a cavity fault).
* If a mixed outcome (some rows each) -> reported per row, no single label.
For the exception: if the exception follows the subnormal coordinate (the control S1 throws too, or the ladder stops at a stated exponent) -> subnormal arithmetic in the exact expansions or CDT, not the cavity.
**Not claimed.** Anything about other families, other platforms (Apple M1 only), or whether the fix is easy. No pipeline, validator or Geogram source is changed by V3; if a refusal rule is proposed it is only proposed. Sample points of the scorer sit on a 2^-14 grid and cannot see features below that size; volumes are what detects them.
**Run after the diagnosis:** the fast suite, the mutants and the acceptance tests (unchanged code, to show nothing broke).

### MP11: hybrid narrow phase (GPU filter, CPU exact)
**Question.** Given the candidate pairs from MP10, can a GPU triangle-triangle filter discard most pairs with definite-no answers, leaving only the rest to the exact CPU test, with the final answer identical to the all-pairs exact CPU result?
**Design.** Per candidate pair (a triangle of A, a triangle of B) the shader computes the signs of orient3d(a0,a1,a2,b_i) (3 signs) and orient3d(b0,b1,b2,a_i) (3 signs) with the MP09 stage-A filter (soft binary64, conservative error bound), each sign being +, -, 0-certain or UNCERTAIN. Verdict NO if all three B signs are definite and strictly equal, or all three A signs are definite and strictly equal (disjoint planes side); otherwise MAYBE. A third verdict YES (both triangles' vertex signs definite and mixed, and the coplanar-free interval test definite) is optional and reported separately; the gating output is NO/MAYBE. MAYBE pairs go to the CPU exact triangle-triangle test (the repository's exact predicates, cpp_int where needed). Distance variant: the shader computes, per pair, a lower bound of the distance between the two triangles from their boxes widened outward (binary64 boxes rounded outward), culls pairs whose lower bound exceeds the best exact upper bound found so far (host loop in rounds), CPU exact on survivors.
**Bars (all hard unless marked reported).**
1. **Equality of answers.** For every case: the set of intersecting triangle pairs (and the boolean 'any pair intersects') from GPU filter + CPU exact equals the all-pairs exact CPU result (brute force up to 4e8 pair tests, otherwise the BVH-pair result `cpu/bvh_ref.h` plus exact on the same widened boxes, with brute force on a 1e5-pair sampled sub-problem as cross-check). For the distance variant: the exact squared distance (as an exact rational printed), and the argmin pair (ties broken by lowest (a index, b index)), equal the all-pairs exact CPU.
2. **No false NO.** The number of pairs the GPU labelled NO that the exact CPU says intersect is 0 on every class below (counted explicitly, not inferred from the final answer).
3. **Classes.** random triangle soups; sphere/torus/icosphere pairs (translated, interpenetrating, touching, disjoint, nested); face/edge/vertex-touching lattice; coplanar overlapping; coplanar disjoint; identical meshes; one-ulp and 2^-40 perturbations; huge offsets (2^30, 2^50); the corpus touch sets (read via the existing generators, hashes as recorded); and the 407 real-mesh pairs if the cached data exists locally (reported, optional).
4. **Determinism.** 20 repeats give byte-identical verdict arrays; M1 and lavapipe (x86_64 and aarch64 in CI) give identical NO/MAYBE arrays or, where they differ because filter uncertainty legitimately differs by driver, identical final answers (the final answer is the gating output; per-pair array differences are reported).
5. **Overflow and fallback.** With a pair cap below the true count the error flag is set and the CPU fallback answer equals the reference.
6. **Planted mutants, each caught by at least one class:** (m1) MAYBE treated as NO (missing CPU fallback for uncertain), (m2) error bound off by one ulp-class (bound too small), (m3) a candidate pair dropped (last pair of each workgroup), (m4) strict inequality replaced by non-strict in the all-same-sign test, (m5) distance cull using the lower bound without outward rounding.
7. **Reported (not gating).** Uncertain/MAYBE rate per class; fraction of pairs the filter discards; time of GPU filter + CPU exact versus CPU-only exact (1 thread and 8 threads), upload and readback included, for few-large and many-small shapes; M1 numbers are provisional G4 evidence, lavapipe numbers are not.
**Out of scope.** Triangle-triangle intersection geometry (the exact CPU result is the oracle, constructing intersection points is not part of this POC); booleans on the GPU; the T4.

### MP12 amendment (registered 2026-11-15, before any MP12 code)
**Design.** (a) Point-in-solid: for each query point, a ray along +x, parity of crossings with the BVH-candidate triangles (MP10); each crossing test uses the MP09 filter (soft binary64) and returns IN/OUT/UNCERTAIN per triangle; any UNCERTAIN triangle (ray through an edge, vertex or the plane) sends the whole query to the exact CPU test (`harness/pip.h`). (b) Volume and area: exact accumulation. Each triangle's signed-volume term is computed exactly (exact multiply added to `f64soft.inc`, or integer limbs) and accumulated into a wide fixed-point/expansion accumulator, so the result does not depend on thread count or order; one final rounding.
**Bars (hard unless marked).**
1. Point-in-solid answers equal the exact CPU on every query in: random points in/around sphere, torus, cube lattice; points on faces, edges and vertices; points at 1 ulp, 2^-40 from the surface; rays through vertices; meshes at offsets 2^30 and 2^50; at least 1e6 queries in total, each class named.
2. No false definite answer: the count of GPU IN/OUT verdicts that differ from the exact CPU is 0 (counted per query, not per class).
3. Volume and area are bit-identical to the exact oracle's correctly rounded value (`harness/exact.h` rational recompute) on every mesh of the corpus including the 2^-30, 2^30 and 2^200-scale copies, and bit-identical for 1, 4 and 8 CPU threads and across repeated device runs (20); M1 versus lavapipe (CI) bit-identical (reported if lavapipe is not available for the run).
4. Overflow/underflow: inputs outside the filter's exponent window go to the CPU exact path; a class covers them and the answer still equals the oracle.
5. Planted mutants, each caught: parity off by one for rays through a vertex; UNCERTAIN treated as OUT; bound ignored; exact accumulation replaced by plain binary64 sum; accumulator carry dropped.
6. Reported: UNCERTAIN rate per class; time against 1- and 8-thread CPU, upload and readback included, few-large and many-small; M1 numbers provisional.
**Out of scope.** Winding-number prefilter (MP15), distance, T4.

### MP13 amendment (registered 2026-11-15, before any MP13 code)
**Design.** A wrapper around MP11/MP12 with: startup self-test (known-answer cases on the device; any mismatch disables the GPU path), a sampled runtime shadow check (every k-th batch recomputed on the CPU; a single disagreement trips the breaker for the process), a circuit breaker (N consecutive failures or any disagreement: CPU only, with a recorded reason), and a CPU path that is always the reference.
**Bars (hard).**
1. For each injected fault: device lost mid-batch, out of memory at allocation, no Vulkan device, shader load failure, pair-buffer overflow, MAYBE rate over a configured cap, deadline expired, a kernel that returns a wrong answer (planted), the answer returned equals the CPU-only answer byte for byte and the reason is reported; 0 crashes, 0 hangs (each case has a timeout).
2. The shadow check detects a planted wrong GPU answer within k batches (k configured, tested at k = 1 and k = 8) and trips the breaker; after tripping no GPU result is returned.
3. The self-test fails on a planted wrong kernel and passes on the real one.
4. Crossover: sweep 1e2..1e7 triangles and 1..1e5 meshes, GPU path including upload/prewarm versus the best multi-core CPU path (8 threads, never one thread); report the crossover size, or that none exists on this device. The bar is the report, not a particular value.
5. Planted mutants, each caught: breaker never trips, shadow check skipped, fallback returns the partial GPU result, self-test always passes.
**Out of scope.** Real device-loss on hardware (injected only), T4, extension integration (MP14).
