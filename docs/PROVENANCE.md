# Provenance

What came from where, what is fetched and not vendored, what was changed on the way in, and what was left out.

## Origin

exactmesh was developed on a research branch of a fork; the fork commit is `5f113ccbd7e13128bb4ed43050fe9be1fc334660`, and the full history (every experiment, report and recorded run, including those not carried over here)
is on that branch of the fork under the `zrecore-org` organization. This repository was assembled from that commit by extracting only the mesh-related files under one directory of it (`git archive` of the commit; no uncommitted file was copied; nothing from
the fork's server source tree, from its database-extension spike, from its aggregation proofs of concept, or from its planning notes was used). Large generated corpora that the research branch had committed (`corpus2d/cases`, `corpus3d/cases`, `corpus_hard/cases*`) were
**not** copied: they are regenerated byte-identically by the generators and checked against the recorded `EXPECTED_SHA256*.txt` files.

## Fetched, not vendored

Nothing third-party is vendored. Every item is downloaded by a script from a pinned URL and verified against a recorded sha256 (or, for Manifold, a pinned commit) before use; the table of pins is in `REPRODUCE.md`.
Geogram v1.10.1 (BSD-3-Clause, built without TetGen, Triangle and HLBFGS), Boost 1.88.0 headers (BSL-1.0), Shewchuk `predicates.c` (public domain), Catch2 v3.16.1 (BSL-1.0), Vulkan-Headers and volk (Apache-2.0/MIT, MIT), Manifold v3.5.5 with Clipper2 (Apache-2.0, BSL-1.0; optional comparison only).
The Shewchuk hash was recorded on first fetch from the author's page (trust on first use) and has not been cross-checked against a second source. GitHub source-archive hashes were recorded on 2026-11-14.

## Frozen files and the adaptations that were unavoidable

Sources whose bytes are pinned by hash records made before the corresponding runs are byte-identical to the research branch and were **not** given SPDX headers (a header would change the hash and invalidate the pre-registration); their licence is declared in `REUSE.toml`.
Five pinned *scripts* hard-code the research branch's directory layout and could not run unchanged; they were replaced (the original hash records are kept verbatim in the records that cite them). One record also had an absolute path rewritten:

| `lib/geogram/mp24b/score_fidelity2.py` | `afa0281d3aa35422c9f120ca92d5d767e038937e1956b16cb227e14be7fe7950` | same file with two lines changed (`ROOT` depth, `mesh_compare` path) plus an SPDX header |

| `corpus/fidelity2/build_gen_fidelity2.sh` | `a52e241659ab9131c4ac5208e00e54cb75ae8817742d7e8c987ec22ca4d5047b` | CMake target `gen_fidelity2` and `ci/geogram_xplat.sh tools24b` (flags `-O2 -ffp-contract=off`, as before) |

## Clean-room statement for the soft binary64 code

`gpu/shaders/f64soft.inc` (exact IEEE-754 binary64 addition and multiplication in 64-bit integer arithmetic, one text compiled as C++ and as GLSL) was written from the IEEE 754 semantics for this project.
The *idea* of emulating exact binary64 in integers rather than float pairs came from the plan of a sibling project (a GPU-accelerated database fork under the same organization, whose design notes describe such a kernel); **none of that project's source was read and no code was copied.**
The multiply, the helpers and the mutation switches were written for this project. The file previously also contained a summation routine for the host project's aggregation operator; it was removed on extraction and nothing here depends on it.

## Lock scripts

`tools/with_gpu_lock.sh` and `tools/t4_ci_turn.sh` coordinate use of one shared GPU (and one shared hosted runner) with other projects of the same organization. `with_gpu_lock.sh` was adapted on the research branch from a lock script of a sibling project (a fork of the PostgreSQL extension PG-Strom, whose
upstream is under the PostgreSQL License) and "shares some lines with it". Only the header comment differs from the research-branch copy; the lock path and protocol are unchanged on purpose, so that runs of this repository and of the sibling project never overlap on the GPU.
**Open licensing question for the owner:** if lines of that script are derived from a PostgreSQL-licensed work, the PostgreSQL License notice may need to be added to `NOTICE` and the Apache-2.0 SPDX header on that file reconsidered. This was not decided here.

## Scrubbing audit

`grep -rniE 'mongo|pg-strom|pgstrom' .` over this repository finds only the following, all intentional:

| Where | What | Why it stays |
|---|---|---|
| `tools/with_gpu_lock.sh` | `PGSTROM_TEST_LOCK`, `/tmp/pgstrom_test.lock`, `TREE="exactmesh ..."` (changed from the research label) | the shared lock path and variable of the protocol (a different path would defeat the mutual exclusion); `TREE` is the label other waiters see |
| `tools/t4_ci_turn.sh` | the default `REPOS` list names the other two repositories that share the T4 runner | needed to see the runner's busy state across repositories |
| `docs/PROVENANCE.md` | this file | explains the above |

Everything else was removed or rewritten: the host project's source, build files and planning notes; its aggregation proofs of concept; its database-extension spike; the planning, resource and delegation sections of the plan and the extension spike
and gate G5 of the results log; the host-specific parts of the licence audit and parity matrix (the "in-tree" and "vendored" statements about the host's source tree); the summation routine in `f64soft.inc`; absolute paths of the research machine.

## Left out on purpose

The aggregation proofs of concept and their shaders, the database-extension spike, the build system of the research branch, Slang and Bazel experiments, the real-mesh download script and pin, the per-step `REPORT.md` files, the Embree, plane-based and Cherchi-survey spikes, the MP18 guard and MP20-MP22 development tooling
(their frozen outputs and patches are kept), and every generated corpus. They remain in the research branch's history.
